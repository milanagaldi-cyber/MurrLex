Administration model and operating guide

Build {{ build_version }} · updated {{ build_updated }}

This guide describes the current production authorization model. Product login, Lexamora Studio access, Django Admin permissions and operating-system access are separate layers. A permission in one layer never silently grants a permission in another.

Four administration layers

LayerWhat it controlsWho manages it
Product accountLogin, Google identity, account status, subscription, AI entitlement and application sessions.Django superusers and delegated staff roles in this Admin.
Lexamora StudioWorkspace ownership, workspace membership, project sharing, editing, translation, AI generation and export rights.Workspace owners/admins, project controllers and server super administrators.
Django AdminUsers, groups, provider keys, AI grants, operational records, audit and support actions.Accounts with is_staff and the required Django permissions.
Server administrationLinux, SSH, Nginx, systemd services, PostgreSQL, storage, secrets, deployment and backups.Infrastructure administrators with an individual SSH/sudo account. This access is not created from Django Admin.

Superuser and Superadmin

No user becomes a Django superuser automatically. The first registration, first Google login, a specific email address, workspace ownership or project Full control never grants superuser status.

A Django superuser has the explicit is_superuser flag. It is created through a controlled createsuperuser operation or assigned by an existing Django superuser. Google-created users start as ordinary active users with Staff and Superuser disabled.

The Superadmin group is the delegated server-application administrator. It receives synchronized Django model permissions and global Lexamora Studio administration, including access to all active workspaces/projects, workspace owner transfer and bulk user selection. It is still not a Linux administrator and cannot read provider secrets after they are stored.

A server/Linux administrator can deploy and recover the service but does not automatically receive a product account. For traceability, infrastructure work and product administration should use separate named accounts.

Workspace roles and rights

RoleRights
OwnerView, edit, translate, manage members/projects, use AI, export and archive. Exactly one owner is recorded. Only a server super administrator can transfer ownership.
AdminSame operational capabilities as Owner, except ownership itself and owner-only revocation safeguards.
EditorView, edit and translate workspace content. AI/export/member management require an explicit entitlement or higher role.
TranslatorView and translate without general content administration.
ViewerRead-only workspace access.

An active workspace member inherits access to projects in that workspace unless a specific project records an exclusion. Workspace AI access and the account-level AI grant must both permit the operation.

Project roles and rights

RoleRights
ViewRead the project and its accessible media.
EditView, edit, translate and use AI when the user also has account/workspace AI entitlement.
Full controlEdit plus project management and export. It does not make the user workspace owner or Django administrator.

Project-only access can be added in addition to inherited workspace access. The workspace owner cannot be removed from an individual project. A workspace owner may revoke inherited project access for another member without removing that member from the workspace.

Working with users: onboarding workflow

  1. If Google staging access is restricted, add the address to Google OAuth Allowed Users.
  2. Ask the person to sign in once. The login creates a basic active account, never Staff or Superuser.
  3. Open Users and verify identity, email and active status. Do not enable Staff for ordinary product users.
  4. Use AI Access for server AI entitlement. Never put provider API keys into user, workspace or project fields.
  5. Share the workspace or project from Lexamora Studio. Use the smallest suitable role and verify inherited project access.
  6. For Admin work, enable Staff and assign one minimal role group. Only a real Django superuser may change staff, superuser, groups and direct permissions.
  7. Require TOTP for staff when the MFA policy is enabled. Verify recovery requests out of band.
  8. For departure or compromise, revoke Studio access, active sessions and AI entitlement first; then block the account. Physical user deletion remains disabled for audit integrity.

Operational safety

  • Use named accounts. Never share a Django superuser or SSH login.
  • Use least privilege and review Superuser, Superadmin, Staff, MFA and workspace owners regularly.
  • Provider keys are entered through Provider Keys, encrypted at rest and never displayed again.
  • Workspace/project sharing is not the same as Django Admin access and is not the same as AI entitlement.
  • Critical changes should leave an Audit Log record and a human-readable reason.
  • Linux administrators maintain deploys, services, database, backups and secrets. Product admins maintain people, roles and content.
