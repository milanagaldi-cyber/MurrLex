Administration model and user guide

This page describes the current production access model. Application accounts, Django staff roles, Django superusers, and Linux server accounts are separate security layers.

Who is a superuser

No user becomes a Django superuser automatically. The first Google login, the first registered account, an email address, workspace ownership, or membership in a project never grants this status.

A Django superuser is an account with the explicit is_superuser flag. It is created with the controlled createsuperuser command or granted by an existing Django superuser. Google-created users are explicitly created without staff or superuser rights.

The Superadmin group receives all current model permissions, but group membership does not set is_superuser. Code paths reserved for a real Django superuser remain unavailable to a group-only administrator.

Capabilities

RolePurpose and authority

Superadmin groupAll synchronized Django model permissions and delegated Studio administration. It does not bypass explicit superuser-only safeguards.

Working with users

  1. Add the email to Google OAuth Allowed Users when Google staging access is restricted.
  2. Ask the user to sign in once. Google login creates a basic active application user without staff or superuser rights.
  3. Open Users. Keep ordinary product users active but leave Staff and Superuser disabled.
  4. For Admin access, enable Staff and assign the smallest suitable group. Only a real superuser can change staff, superuser, groups, and direct permissions.
  5. Use AI Access to enable server AI functions. Project or workspace sharing and AI entitlement are related product permissions but are not the same as Django Admin access.
  6. Share a Lexamora workspace or project from Studio. Project roles are View, Edit, or Full control; workspace ownership is managed separately.
  7. Use audited bulk actions to block, unblock, mark for deletion, or grant credits. Physical user deletion is disabled.
  8. Require TOTP for staff when the Admin MFA policy is enabled. MFA recovery must be verified out of band and recorded in Security Audit Log.

Safety rules

  • Use individual staff accounts; never share a superuser login.
  • Grant the least powerful role that can complete the job.
  • Do not store OpenAI or ElevenLabs keys in user records or project fields; use Provider Keys.
  • Critical actions require a reason and are written to the audit log.
  • Review staff, superusers, groups, MFA and break-glass accounts regularly.
